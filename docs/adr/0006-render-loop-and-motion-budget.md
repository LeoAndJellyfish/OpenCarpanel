# ADR-0006：遥测渲染使用独立 rAF 循环和运动预算

## Status

Accepted

## Context

UDP 样本到达并不严格对齐屏幕刷新。如果每个网络消息直接触发组件树重渲染，容易产生抖动、无效工作和掉帧；如果对所有值使用长缓动，又会把视觉读数落后于真实状态。用户同时要求优秀动态效果、低延迟和高帧率。

## Decision

网络层只更新最新遥测目标；驾驶视图由一个 `requestAnimationFrame` 循环读取目标并驱动需要连续运动的组件。连续值最多按预期的一个采样周期做短插值，关键离散值立即提交。组件只订阅声明字段，编辑器和手势代码分包懒加载。

预设 UI 动画优先使用 CSS/WAAPI，只改变 transform、opacity 和必要颜色。60 FPS 是基线验收目标，120 FPS 是支持设备上的增强目标。所有运动随 `prefers-reduced-motion` 提供温和版本。

## Consequences

### Positive

- 网络抖动不会直接变成视觉抖动。
- 高频数据不会导致整个 Preact 树每帧重渲染。
- 关键读数不因装饰缓动延迟。
- 驾驶视图初始包不承担编辑器动画库成本。

### Negative

- 需要维护网络时钟、目标状态和显示状态三种概念。
- 插值、断流和恢复必须有确定规则并在真机调试。
- 组件作者需要遵守严格的 DOM、绘制和动画预算。

### Neutral

- 优秀动态来自数据响应和状态层次，不以动画数量作为目标。

## Alternatives Considered

- **每个包直接 setState：** 简单但到包节奏与渲染节奏耦合。
- **所有组件使用 CSS transition：** 新目标持续重定向会产生视觉滞后。
- **驾驶页常驻大型动画库：** 对主要是遥测插值的场景收益不足。
