# ADR-0002：使用 Adapter API 与统一遥测模型

## Status

Accepted

## Context

F1 24、欧卡/美卡、地平线等游戏的数据来源、字段命名、单位和更新节奏不同。如果 UI 直接读取游戏结构，每增加一个游戏都会复制组件并扩散条件判断。另一方面，强行把所有游戏字段塞进一个固定结构会造成语义含糊和大量伪造默认值。

## Decision

每个游戏通过独立 crate 实现 `GameAdapter`。适配器把字节输入转换成统一的状态更新和离散事件。核心字段使用稳定语义、SI 单位与显式缺失值；能力清单声明当前适配器提供哪些字段。暂时无法标准化的数据进入 `extensions.<adapter_id>`。

MVP 的适配器编译进 Host，不支持运行时加载第三方本地库。

## Consequences

### Positive

- UI 和 Widget SDK 不需要知道 F1 24 packet id。
- 同一组件可以跨游戏复用，并对不支持的数据给出明确 fallback。
- 单位转换、会话切换和错误处理集中在适配器/核心边界。
- 第二个游戏能成为架构有效性的直接测试。

### Negative

- 需要谨慎治理字段语义和 schema 版本。
- 某些游戏专属能力只能通过 extension 暂时暴露。
- 编译进 Host 意味着增加适配器需要发布新版本。

### Neutral

- 只有出现真实社区插件需求后，才评估 WASM 或子进程协议；Rust ABI 不作为稳定插件接口。

## Alternatives Considered

- **UI 直接使用游戏结构：** 初期快，但形成游戏耦合和重复组件。
- **完全动态键值字典：** 扩展方便，但失去编译期类型、单位语义和可发现性。
- **所有字段进入巨大固定结构：** 简单但会快速膨胀并误用缺失值。
